# Version Management

This fork retains upstream's semantic-versioning and release configuration, but does not publish binaries. Its installer downloads the native diff library and Linux OpenMP runtime from [upstream CodeDiff releases](https://github.com/esmuellert/codediff.nvim/releases), using the unchanged root `VERSION` file. The watcher has a separate upstream repository and version; see [automatic installation](../README.md#automatic-installation).

Do not bump `VERSION` merely for fork-only Lua or documentation changes: the installer needs a matching upstream native release. A native ABI change would require a coordinated library build and installer-source change, not just a version bump.

## Inherited release policy

The checked-in [`cliff.toml`](../cliff.toml) and [release workflow](../.github/workflows/release.yml) describe the inherited publishing machinery. Git tags and Conventional Commit messages determine its next release through git-cliff; contributors do not edit `VERSION` manually as part of that flow.

| Change | Version effect |
|---|---|
| `fix:`, `perf:`, `revert:`, or `refactor:` | Patch |
| `feat:` | Minor |
| `type!:` or a `BREAKING CHANGE:` footer | Major |
| `test:`, `docs:`, `chore:`, `build:`, `ci:`, `style:`, `format:` | No release |

Use a commit type configured in `cliff.toml` when a PR should communicate a release level. Unrecognized titles are ignored rather than forcing a release.

Examples:

```text
fix(explorer): preserve selection after refresh
feat(history): filter commits by author
feat!: replace the configuration schema
refactor(view): split rendering modules
```

Under this policy, these request patch, minor, major, and patch releases respectively.

## VERSION

`VERSION` records the native version expected by the plugin. Lua and CMake read it so native-library builds and download URLs use the same version. In this fork, it remains aligned with the upstream binary source.

During a release, CI calculates the next version and applies it to each build workspace before compiling. After every native artifact passes, the release job commits the same value to `VERSION` and tags that commit.

Do not edit `VERSION` or create release tags manually. The release check fails if `VERSION` differs from the latest reachable version tag.

## Inherited automated release flow

The workflow is configured for pushes to `main`, excluding changes limited to root Markdown files, `docs/**`, or `dev-docs/**`. If enabled in a repository with the required publishing credentials, it runs:

1. git-cliff reads commits after the latest release tag.
2. All native platforms build and test with the calculated version.
3. CI requires the complete release asset set and creates `SHA256SUMS`.
4. The publish job verifies that `main` has not moved while artifacts were building.
5. A GitHub App atomically pushes the `VERSION` commit and annotated tag.
6. GitHub creates the release with generated notes and the verified assets.

If no commit requires a release, build and test still run for a triggered workflow, while asset assembly and publishing are skipped. Documentation-only pushes matching the path exclusions do not trigger it.

Only the publish job receives write permission. If `main` advances during a build, that run publishes nothing; the queued run recalculates the release from the newer revision.

GitHub release notes remain generated by GitHub. git-cliff owns version calculation, not release-note formatting.

Publishing requires the repository's `APP_ID` variable and `APP_PRIVATE_KEY` secret for a GitHub App, plus permission to push the release commit/tag and create releases. The presence of this inherited workflow is not a promise that fork pushes publish assets, and it does not change the installer's upstream download source.
